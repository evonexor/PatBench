# Pipeline: what each stage does

There is one directory per stage (`pipeline/NN_...`), numbered in the order the data flows. This page gives, for each
stage, its **inputs, outputs and key decisions**, and how to start it from this repository. Figures come from the run
records of the stages; the data they describe are not in this repository.

```
archives -- 02 extract ----------+
archives -- 04 structure catalog +-> 03 recovery -> SAR_merged --+-> 05 target mapping -> target_map ---+
                                                                 +-> 06 validation sample + annotation -+
public databases -- 01 standardise ---------------------------------------------------------------------+
                                                                                                          |
SAR_merged -> 07 structure repair -> SAR_merged (repaired) ------------------------------------------+   |
                                                                                                      v   v
                                                              08 build -> release directory -> 09 structures
                                                                                              -> 10 evaluation
                                                                                              -> 11 support tables
                                                                                              -> 12 provenance check
```

| Stage | Scale | Can it be re-run from this repository? |
|---|---|---|
| 02, 04, 03 | 345,940 archives, 20 processes, hours to days | Code and commands are complete and frozen (see [CODE_PROVENANCE](CODE_PROVENANCE.md)); not treated as routine steps |
| 05, 06 | include curation and annotation by sessions or people | The deterministic parts are scripts; the curation results are data and are not regenerated by scripts |
| 07 | minutes to hours (opens the raw archives) | Commands are registered as steps; the input is the release built before the repair |
| 08 | minutes to tens of minutes | `patbench release` |
| 09 | downloads public structure files | `patbench run fetch-structures` |
| 10, 11, 12 | seconds to minutes | `patbench run ...` |

## 00 Operations scripts (`pipeline/00_ops/`)

- `copy_patent_data.py` copies the patent archives from a NAS to the server's dedicated SSD, with rsync, checksums and retries. It hard-codes the paths of those two machines and is kept as run; **reference only**.
- `launch_recovery_service.py` checks the pre-flight results of the recovery stage (code hash, the verification report of 50 fixed archives) and then starts the recovery as a systemd service. It is bound to that server as well.

## 01 Public databases (`pipeline/01_public_data/`)

- Input: the BindingDB patent TSV (2026-09), the ChEMBL 37 patent activity sources (SRC_ID 37 and 38), the 48 H-bench targets of HARVEST, and SureChEMBL.
- Output (`raw/patent-data/standardized/`): `BindingDB.parquet`, `ChEMBL.parquet`, `HARVEST.parquet`, `SureChEMBL.parquet` with the standard columns `Patent, Target, Activity Type, Relation, Value, Unit, SMILES, UniProt` followed by the original source columns. Nothing is merged across databases or de-duplicated.
- Use: PatBench uses these tables to ask how much of the extracted data is already public (`08_build/novelty.py`, `08_build/public_overlap.py`). The public comparison set **excludes** HARVEST because its snapshot is only the H-bench subset. See [pipeline/01_public_data/README.md](../pipeline/01_public_data/README.md).

## 02 First extraction (`pipeline/02_extract/`, version 0.8.0-full)

- Input: `manifest.json`, the list of the 345,940 US patent MOL archives.
- What it does: reads the activity tables from the patent XML and maps table rows to MOL files in the archive by compound number. **The formal SAR contains only compounds whose number links directly to a structure row.** The compound number, the activity column and cell, the target, the unit and the nM conversion are checked independently against the raw XML, and the SMILES/InChIKey computed from the raw MOL are checked for consistency. Structure-image associations with neighbouring examples are listed as candidates only and are not mixed into the formal SAR.
- Output (`results/`): `SAR` (the original 17 columns), `SAR_enriched`, `SAR_with_evidence` (adds the raw cell, the structure and activity locations, the source and the verification evidence), `candidate_SAR`, `review`, `structures`, `patents` (archive status and patent metadata), `molfiles/`, `bibliography/`.
- Entry point: `python pipeline/02_extract/run_full.py --root <archive root> --manifest <manifest> --output <output> --workers 20 --full`. Code hash `148c103f...` (see `provenance/STAGE_HASHES.json`).
- Unit tests shipped with the stage: `test_pipeline`, `test_documents`, `test_metadata`, `test_xml_source`, `test_alignment`.
- Note: some descriptive metadata values written by this stage and by stage 04 (for example the `indication` and `technical_field_source` columns of `patents`) are Chinese-language labels. The PatBench build reads only the date columns of `patents` and never these.

## 04 Structure catalogue (`pipeline/04_catalog/`, version 0.9.1-sharded-aggregation)

- What it does: extracts every MOL of every archive regardless of domain and of whether it has activity, plus CDX/SDF sources without a same-named MOL, patent sequence listings and UniProt accessions marked explicitly in the patent. Results go to `results/`; per-archive intermediate checkpoints go to `results/checkpoint_cache`.
- Relation to PatBench: **the recovery stage reads its checkpoints** (`CAT` in `03_recovery/activity_recovery.py`), and the context extraction of the target mapping reads its result tables. The PatBench build scripts do not read it directly.
- The directory contains the same five modules as `02_extract` (byte-identical, guarded by tests) plus `structure_catalog.py`, `catalog_annotations.py`, `catalog_metadata.py`, `run_structure_catalog.py` and `get_structure.py`. Code hash `67b554fd...`.

## 03 Recovery of activity links (`pipeline/03_recovery/`)

- Input: the checkpoints and `SAR.parquet` of the first extraction, the checkpoints of the structure catalogue, and the raw archives.
- What it does: the first pass excluded or failed to link many archives. The recovery works in phases: `review_only` (25,703 patents with review records only), `previously_skipped` (236,178 archives that the first pass excluded, left undecided, or could not parse, including old formats) and `remaining_processed` (84,059 other archives, searched for omissions). It uses only evidence that is explicit within the same archive: compound numbers, structure references, assay headers, target or assay object, and units. Where an A/B/C or plus-sign legend is defined in the text, the threshold or interval is kept (the relation or the bounds are stored; no point value is invented). Mass concentrations, mass doses, pIC50 and similar are stored as extended activity and are not converted.
- Output (`results/`): `new_SAR`, `verified_extended_activity`, `remaining_review`, `SAR_merged` (the original 395,143 formal SAR records plus the new numeric SAR = 603,908 records), `patents` and the per-phase reports.
- Entry point: `python pipeline/03_recovery/run_recovery.py --manifest ... --output ... --workers 20`. Code hash `81fd6891...`; the code has four hard-coded path constants, see [REPRODUCE](REPRODUCE.md).
- Unit tests shipped with the stage: `test_recovery` (18 positive and negative tests).

## 05 Target mapping (`pipeline/05_target_map/`)

Maps every (patent, assay label) pair to a UniProt accession. It ran in three rounds: **v1** covered only the candidates for affinity ranking (6,878 pairs), **v2** extended this to all 13,557 pairs of `SAR_merged` and all endpoints, and **v2.1** corrects three accessions. Each of v1 and v2 consists of:

1. **Deterministic layer** (`candidates.py` / `v2_candidates.py`): reads species and mutations from the label and proposes candidate identities from the ChEMBL cell-line vocabulary, the alias dictionary (`build_dictionary.py`) and cross-references to the public databases.
2. **Patent text context** (`patent_context.py` / `v2_context.py`): fetches title, headers and assay descriptions from the raw patent XML for the curation step.
3. **Curation** (`make_batches.py` / `v2_make_batches.py`, then curation, then `read_curation.py` / `v2_read_curation.py`): turns each pair, its candidates and its context into an item; a curator (a session) decides the identity, a confidence (H/M/L) and, in v2, whether the pair is mappable at all. **The curation result is data and is not regenerated by a script**; the scripts only produce the items and read the results back robustly (repairing lines with one tab too many or too few).
4. **Sequence resolution and assembly** (`resolve_lib.py`, `fetch_unresolved.py`, `fetch_round2.py`, `assemble.py` / `v2_assemble.py`): resolves the curated gene symbols and species to accessions and sequences through the UniProt REST API (reviewed entries first).
5. **Cross-reference and finalisation** (`xref_refs.py`, `xref_bindingdb.py` / `v2_xref.py`, `finalize.py` / `v2_finalize.py`): compares with BindingDB and ChEMBL records of the same patent and molecule; writes `target_map.parquet` and the coverage statistics.
6. **Spot checks** (`spotcheck_extract.py` / `v2_spotcheck_extract.py`, `v2_spotcheck_verdicts.py`): extracts a longer evidence window for a sample, judged by a person against the patent text (115 judgements were recorded for v2).

- **v2.1** (`v2_1/apply_target_overrides.py`): `fetch_unresolved.py` resolved free-text identities (`ORG:species|name`) by a full-text UniProt search and kept the longest hit without checking that it was the protein named. Three identities came back as the wrong protein (NDM-1 as GroEL, VIM-1 as an aminoglycoside phosphotransferase, Mtb LeuRS as IleRS). The override table `target_overrides.tsv` lists the old accession, the identity, the new accession, the expected number of rows and a word that must occur in the new record's protein or gene name; every other row of `target_map.parquet` is copied unchanged.
- Output: the build reads `target-uniprot-map-v2.1-20261031/target_map.parquet` (rows of v1 are merged in and labelled by `source_run`). In the r6 build log, 11,761 of the 13,557 distinct (patent, label) pairs (86.8%) appear in the map; this only means a row exists, not that the pair maps to a protein. `target_mapped` (high or medium confidence, a single wild-type protein) is true on 350,664 rows (58.1%).
- `explore2/3/4.py`, `export_chembl.py` and `extract_bindingdb.py` are the exploration and public-database extraction scripts of v1.

## 06 Validation (`pipeline/06_validation/`)

- `build_sample.py` draws a stratified sample and builds **blinded** evidence pages from the patent XML (400 items); two independent annotation rounds follow (both annotators were automated sessions); `merge_annotations.py` and `analyze_agreement.py` merge them and compute agreement and accuracy; `build_adjudication_items.py` builds the queue for adjudication (61 disagreements, **expert adjudication has not been done**).
- `pointer_check.py` and `structure_check.py` check that the MOL file the pipeline points to really contains the structure it claims (20,379 stratified random records, 100% found).
- `failure_modes.py`, `group_level.py`, `diagnose_tables.py` and `diagnose2.py` quantify and detect the two failure modes found by the annotators (substituent fragments and MOL abbreviations).
- Outputs enter the build as three hold-out flags: `pair_validated_error`, `pair_under_adjudication`, `patent_has_validation_issue`. See [VALIDATION](VALIDATION.md).

## 07 Structure repair (`pipeline/07_structure_repair/`)

ChemDraw writes an abbreviated group (F3C, MeO, NH, ...) in a MOL file as **one placeholder atom plus an alias line**; the placeholder atom is always written as element C and the real atom or group is only in the alias text. RDKit drops the alias, so the placeholder becomes a carbon. This changed the stored structure of 128,062 rows (21.2% of the formal SAR) before the repair. Stage 07 repairs the structures of `SAR_merged` and writes a **copy** of the recovery results; the original directory is not touched. The input is the release built before the repair (r5 in the reference run).

| Step | Script | What it does |
|---|---|---|
| `alias-scan` | `alias_scan.py` | first scan: structures resting on an alias that adds atoms (flag `structure_alias_suspect`); opens the raw archives |
| `alias-extract` | `alias_extract.py` | collects the MOL files of every record flagged `structure_alias_suspect` and an inventory of their alias lines |
| `alias-scan-all` | `alias_scan_all.py` | the same inventory for **every** structure file, because the first scan treated a bare `H` label as harmless although the placeholder is always C |
| `alias-pubkeys` | `alias_pubkeys.py` | the molecules BindingDB and ChEMBL curated from the same patents (for validation) |
| `alias-repair` | `alias_repair.py` | implementation A: label catalogue, placeholder atom rewritten in place |
| `alias-expand` | `alias_expand_independent.py` | implementation B, written independently of A (labels read byte by byte, a grammar for labels with a caret, valence check per group and sanitisation of the whole molecule, direction check of the label against the bond); **this implementation's result is used** |
| `alias-validate` | `alias_validate2.py` | checks a repair table against the public molecules of the same patents, independent of the MOL files and of the rules |
| `alias-merge` | `merge_final.py` | turns the output of B into the repair table and applies the nitrile step (reversed nitriles N(+)#C(-) restored to the nitrile) |
| `patch-sar` | `make_patched_sar.py` | writes `SAR_merged.parquet` with repaired SMILES and InChIKey plus three columns: `structure_repair`, `SMILES_before_repair`, `InChIKey_before_repair` |
| `alias-scan-final` | `make_alias_scan_r6.py` | writes `work/alias_scan.parquet` for the build: the (patent, molecule) pairs whose stored structure still rests on an alias nobody could expand |
| `list-unresolved` | `list_unresolved_labels.py` | every unresolved label with its context (`structure_repair/unresolved_labels.tsv`) |

Rules: a placeholder atom is rewritten in place to the first atom of the group (so wedge stereo information on its neighbours stays valid). Only labels in the rule table are expanded, nothing is guessed; peptides, polymers, antibodies, Markush placeholders and the like stay as drawn and keep the flag `structure_alias_suspect`, which keeps them out of the task sets. How the repair was validated, and its limits, is in [VALIDATION](VALIDATION.md).

**Nitrile evidence audit** (`07_structure_repair/nitrile_audit/`). After the repair, every conversion of a reversed nitrile was checked against the original drawings. `nitrile_inventory.py` lists the structure files and archives behind the converted records, `nitrile_extract.py` extracts the N(+)#C(-) motifs with their labels, bond geometry and the original image, `nitrile_text.py` collects the patent text around each image, `nitrile_panels.py` builds the image panels for the visual review, `nitrile_finalize.py` writes the decisions per motif, record and row, the derived `sar_all_reviewed.parquet` and the quarantined records, and `nitrile_verify.py` checks the decision tables with the evidence gate `verified_nitrile_guard.py`. The step that produces `motif_evidence_geometry.parquet` and the visual review itself are not scripted (see [CODE_PROVENANCE](CODE_PROVENANCE.md)).

## 08 Build (`pipeline/08_build/`)

`patbench release` runs, in order:

| Step | Script | What it does |
|---|---|---|
| `standardize` | `standardize.py` | keys every molecule to its parent (largest organic fragment, neutralised); heavy-atom count, scaffold, chemistry flags, written to `work/mol_std.parquet` |
| `novelty` | `novelty.py` | whether a molecule, a patent or a (molecule, target) pair is new relative to BindingDB and ChEMBL, written to `work/novelty_flags.parquet` |
| `build` | `build_patbench.py` | gathers all formal SAR, adds provenance, quality and split flags, and cuts the task sets |
| `protocols` | `make_protocols.py` | freezes the few-shot supports (K = 5 and 10, five draws each) and the activity-cliff pairs (ECFP4 Tanimoto 0.85 or more and a difference of 1 log or more) |
| `eval-sets` | `make_eval_sets.py` | complete copies of the ranking tasks for models not trained on PatBench (every group is test) |
| `baselines` / `leaderboard` | `10_evaluation/` | random, heavy atoms, logP, ECFP4 + random forest; scoring and leaderboard |

Two inputs of `build` come from outside the chain and must be in `<release>/work/` first: `public_pairs.parquet` (the (InChIKey, UniProt) pairs of the public databases with their median pAct, step `public-pairs`, `public_overlap.py`) and `alias_scan.parquet` (step `alias-scan-final`, stage 07). The build reads the repaired `SAR_merged.parquet` and the v2.1 target map through the environment variables `PATBENCH_SAR_DIR` and `PATBENCH_TARGET_MAP_DIR`, which `patbench` sets.

What `build_patbench.py` does (details in [SPLITS](SPLITS.md)): parent and stereo sets; the median per (group, molecule); **six unit checks**; label normalisation and duplicate-table detection; repair of bare-number labels (regrouped by header text); attachment of the target mapping; validation hold-outs; fragment groups; one group per series (patent family x protein); time, random and scaffold splits; `test_tier`; first public date; task cuts and `release_manifest.json`.

After the build, the target audit runs: `join_target_map.py` attaches the target map to the groups of the ranking tasks, `make_target_audit.py` writes `target_audit.parquet` (the join plus, per ranking task, membership, time split and test tier), and `audit_targets.py` (network access, three UniProt requests) gives the sequence each group should use (polyproteins cut to the mature chain, named mutants applied, complexes only flagged) and the two checks `label_check` and `xref_status`.

## 09 Target structures (`pipeline/09_structures/`)

`fetch_structures.py <release> <stage>` runs the stages `meta` (UniProt names), `entries` (PDBe best_structures and AlphaFold records), `gql` (RCSB GraphQL: method, resolution, ligands), `select` (choose PDB entries per target and sequence variant), `download` (mmCIF, SIFTS, AlphaFold), `process` (cleaning, ligands, pockets, residue mapping), `groups` (group to recommended structure) and `write`. It contacts only rest.uniprot.org, www.ebi.ac.uk, data.rcsb.org, files.rcsb.org and alphafold.ebi.ac.uk, and parses everything it downloads as data (gemmi) without executing it. `check_structures.py` re-reads the written files and recomputes what the tables claim, printing OK or FAIL for each check. Requires gemmi.

## 10 Evaluation (`pipeline/10_evaluation/`)

`evaluate_patent_bootstrap.py` is the evaluator named as recommended in the freeze record of r6: per-group metrics as below, but confidence intervals resample whole **patents**, models are compared on the same groups (`--reference`), strata are reported and failed predictions are not imputed (`patbench run evaluate`). `evaluate.py` is the build-time evaluator that `leaderboard.py` imports; it computes the within-group Spearman and Kendall correlations, pairwise accuracy (only molecule pairs at least 0.5 log apart), NDCG@10 and the top-10% hit rate within each group, then the median over groups with a bootstrap 95% interval; options `--tier novel`, `--collapse-stereo`, `--cliffs`, `--fewshot`. `baselines_fixed.py` and `leaderboard.py` generate and score the reference baselines. `baselines.py` is the r6 script as it ran; it has a known defect that overwrote the few-shot ECFP4 + random forest predictions with zero-shot ones, and `baselines_fixed.py` is the corrected copy (see [LIMITATIONS](LIMITATIONS.md)). The metric definitions are tested (`tests/test_evaluate.py`).

## 11 Support tables and review page (`pipeline/11_support/`)

- `build_eval_support.py` writes `eval_support/`: the **structural-domain sequence** of every group (the stretch the recommended structure actually models, consistent with the start and end positions in the structure table) and the profile of the test groups of the five ranking tasks (whether the target was seen in training, mapping checks, whether the sequence is long, whether the structure can be used for docking).
- `build_target_names.py` writes the table that gives, for every group, what the target is (accession, gene, protein, organism, mutation) next to what the patent printed.
- `make_review_table.py` writes the manual-review tables of the time-split test groups (reviewer columns blank).
- `review_page/make_review_page.py` generates the manual target-mapping review page (one self-contained HTML file) and writes the test groups of other tasks that are not in the review table.
- `profile_r6.py` and `profile2_r6.py` compute the descriptive profile of a release (size, tasks, splits, tiers, molecular weight, remaining problems).

## 12 Provenance check (`pipeline/12_verify/`)

`provenance_check.py <release> <n_test> <n_train>` draws a random sample of measurements and goes back to the raw patent archives to check four things: the row agrees with the upstream evidence table; `value_nM` and `pAct` can be recomputed from the value and the unit; the text of that cell in the patent XML is `raw_value`; the structure computed from the raw MOL equals the stored structure.

## legacy_v0 (`pipeline/legacy_v0/`)

The build scripts of the first release (2026-10-19) and of the ranking benchmark. PatBench v1.0 was cleaned up on top of them; they are **kept for history only**.
